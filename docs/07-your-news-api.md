# 07 · 接入自己的新闻服务，而不重写 App

这个示例没有擅自读取或修改你现有 `news-aggregator` 的代码、部署和认证。下面是扩展合同，不假定现有 API 路径或字段已经如此实现。

## 第一步：从真实接口建立适配器

在 `src/data/` 增加 `your-news-source.ts`，实现 `NewsSource.page` 和 `NewsSource.article`；为接口响应先写运行时解析和测试，然后再在 `runtime.ts` 注册。扩展 `Source` 联合类型与本地迁移的 source 约束，不硬塞进 `hn` 命名空间。

页面只使用统一 Article，不依赖 Django/DRF 的字段名称。前端 API Base URL 属于公开配置，私钥与采集账号不能随 App 下发。

| 统一字段 | 要从你的后端确认 |
|---|---|
| id / source | 稳定 ID、来源命名空间、迁移规则 |
| title / summary / paragraphs | 真实字段、正文可用性、HTML 与纯文本约定 |
| bodyKind | 缺正文时明确 summary，不拿摘要冒充正文 |
| publishedAt / author / url | 时区、归属、允许访问的原文地址 |
| nextPage / cursor | 实际分页协议；需要 cursor 时扩展接口，不在页面拼分页 |

## 第二步：认证另作独立任务

只有后端需要登录才接认证；不能把“持有新闻站的某个模型 Key”当网站身份。认证任务单独验收登录、刷新、过期、退出、撤销、设备时间异常、跨账户缓存隔离。服务端最终鉴权，App 中的 UI 隐藏不构成权限控制。

## 第三步：同步不是上传 SQLite 文件

将收藏/阅读进度写入本地操作队列，记录稳定 operationId、用户身份、实体版本、幂等重试和冲突策略；服务端回执成功后才确认同步。离线快照和待上传操作分表，退出时按用户隔离，不把账号 A 的队列发给账号 B。

## 第四步：内容处理留在合适的边界

新闻采集、RSS/API 聚合、站外正文提取、翻译/语义处理优先由你已有采集与服务模块完成。移动 App 是阅读与设备交互端，不让每个用户手机重复爬同一来源；也不把未授权正文抓取当成客户端“功能”。

## 可验收任务拆分

A01 公共新闻列表适配 → A02 详情与正文标记 → A03 认证会话 → A04 用户收藏同步 → A05 阅读进度同步 → A06 服务端通知。每项都保留已有 Demo 回归路径，但真实数据失败不能自动伪装成 Demo 成功。
